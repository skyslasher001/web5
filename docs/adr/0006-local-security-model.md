# 0006 — Local security model: loopback, session token, egress gate, policy engine

- Status: Accepted (2026-10-12)
- Date: 2026-10-12
- Flags: security, privacy

## Context

SPEC §17: the system reads files, sees the screen and browses the web. It needs localhost hardening, a kill switch, an offline switch, prompt-injection defence, an audit log and secrets in the OS store.

## Decision

1. **Loopback only.** Core binds `127.0.0.1:47821`. The `Host` header must match exactly (DNS-rebinding defence). `Origin`, when present, must be allowlisted. CORS is enabled for exactly those allowlisted origins (`app://universe`, plus the Vite origin in dev), because the renderer is a different origin from Core. Every other origin is refused before routing. (Corrected during Phase 1; the blueprint said "CORS is disabled", which would have blocked the app itself.)
2. **Per-session bearer token** generated by the supervisor at boot and passed to Electron main and then the preload. WebSockets use single-use 30 s tickets.
3. **Local API keys** for external scripts: scoped (`capture`, `search`), hashed at rest, revocable, shown once.
4. **Supervisor control API** on its own loopback port, with a token only Electron main holds. Code apply/rollback and the kill switch go through it.
5. **Egress gate:** the only module allowed to make outbound connections. It enforces the offline switch, kill switch and per-agent domain rules, and audit-logs every request. A lint rule plus a unit test ban direct HTTP client use elsewhere. Optional Windows Firewall rules come in Phase 12.
6. **Policy engine** on every tool call: tier gate → rules → taint → budget and limits → kill switch (ARCHITECTURE.md §7.3). Agents can't change their own tier or rules.
7. **Consent lives in Electron main** (protected). The backend has no API to turn capture on. Agents can only request it, and you toggle it. Indicators render in an always-on-top layer owned by main.
8. **Secrets** live in Windows Credential Manager via `keyring`, never in config or logs (log redaction filter + test).

## Consequences

- A malicious web page can't reach the API (Host/Origin checks + token).
- Prompt-injected content can at most produce *proposals* that need your confirmation.
- Electron main's protected code is a high-value component: kept small and covered by `tests/protected`.

## Alternatives considered

- **Named pipes instead of TCP:** stronger isolation from browsers, but the SPEC wants a local HTTP API for your scripts, and Host/Origin/token checks cover the browser threat.
